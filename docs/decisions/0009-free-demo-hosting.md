# 0009: Free public demo on Render + Neon

- Status: Accepted
- Date: 2026-11-27

## Context

Hishab is a portfolio project: a reviewer should be able to click a link and use the product. CLAUDE.md
asks for free tools only and to ask before anything needing a credit card. The app needs PostgreSQL, the
.NET API (~300 MB working set, plus headless Chromium while printing a PDF, ADR 0008), Hangfire, and the
static React build. Visitors sign in with the demo button (#91), and the data is reset at startup.

Options considered (all free, checked November 2026):
- **Render (Docker web service + static site) + Neon Postgres:** no card on either. The free API has
  512 MB and 0.1 CPU and sleeps after 15 minutes idle (about a minute to wake). The static site never sleeps.
- **Oracle Cloud Always Free VM:** up to 24 GB RAM, runs our compose file unchanged, never sleeps. Needs a
  credit card to verify, and we would patch and secure a VM ourselves.
- **Own PC + Cloudflare Tunnel:** free and quick, but the demo exists only while the PC is on.
- **Recorded demo only:** no hosting, but nothing to click.

## Decision

Render + Neon, described in `render.yaml` (a Blueprint), set up by hand once (`docs/DEPLOY.md`).
- **API:** the existing `src/api/Dockerfile`, `ASPNETCORE_ENVIRONMENT=Demo`, region Singapore (closest to
  Bangladesh), `/health` as the health check, auto-deploy off.
- **Web:** a Render static site that **rewrites `/api/*` to the API**. The browser sees one site, so the
  refresh cookie (`SameSite=Strict`, `Path=/api/auth`) stays first-party; two `onrender.com` subdomains are
  different sites (it is on the Public Suffix List) and the cookie would not be sent otherwise.
- **Database:** Neon free (scales to zero after 5 minutes idle), the direct (non-pooled) endpoint with
  `SSL Mode=Require`: EF migrations and Hangfire's locks expect a real session, not a transaction pooler.
- **Demo data:** `Demo:Seed`, `Demo:Login`, `Demo:ResetOnStartup` on. Every wake-up starts from clean data.
- **Secrets:** `Otp:HashKey` and `Jwt:SigningKey` generated by Render (`generateValue`); the connection
  string and the Data Protection certificate typed into the dashboard (`sync: false`). None in the repo.
- **512 MB:** .NET heap capped at 200 MiB (`DOTNET_GCHeapHardLimit`), workstation GC, one PDF at a time
  (`Pdf:MaxConcurrentRenders=1`), one Hangfire worker.
- **Client IPs:** `ForwardedHeaders` on with `ForwardLimit=2` (the static site's rewrite plus Render's edge),
  so the per-IP limits on OTP and demo sign-in apply per visitor, not to everyone at once.

## Consequences

- The first visit after 15 minutes idle waits about a minute (the README says so). Neon also wakes up (~1 s).
- Every request goes through two proxies (the static rewrite, then the API's edge): some latency.
- Visitors share one demo shop until the next restart; anything they type is visible to the next visitor
  in the same session window. The banner says so, and nothing personal is asked for.
- If the proxy chain changes (Render changes its edge), `ForwardLimit` must change with it: too low and all
  visitors share a limit, too high and a client can pick its own IP. `docs/DEPLOY.md` has the check.
- Not production: no backups, no SMS gateway, no monitoring, one instance. A real launch would use a paid
  always-on instance, managed backups and a migration step in the pipeline (Program.cs migrates at startup
  only in Development and Demo).
